# Plan: hand the project to your desktop Claude for the Unity port

## Context
You're moving development to your desktop and converting the game to Unity. Your desktop Claude is already working from a ZIP of the repo.

You asked where the plan is. Every plan from this cloud session lives only at `/root/.claude/plans/mossy-mixing-walrus.md`, inside this container. It isn't in the repo, each new task overwrote it, and it disappears with the container. The lasting roadmap is `docs/09-production-roadmap.md`, but it doesn't record the plans or the details of how v0.1 actually works.

Your choices:
- **Plans only:** no code changes here.
- **Godot stays until parity:** CI keeps publishing playable builds until the Unity version plays the same.
- **Engine technicalities are left to the desktop Claude:** what matters most is the **game mechanics and project details**.
- **The desktop works from a ZIP.**

**Outcome:** a set of documents your desktop Claude can read on its own to port the game faithfully. They're committed to the repo, and also sent to you as files, because a ZIP doesn't sync.

## Deliverables (documentation only; no code changes)

### 1. `docs/10-implementation-reference.md`: the game as built (v0.1)
This is the main handoff document. It describes the behavior the Unity version must reproduce. Every number comes from the code or `game/data/*.json`, not from memory. Roster and weapon tables are generated by a script that reads the JSON.
1. **Project at a glance:**
   - Repo layout and the sim/presentation split.
   - How to build, test and run.
   - CI jobs and the `dev-latest` Windows release.
   - Reference state hashes for the determinism parity test (`abc254d66a095c02` at 600 ticks; `d2b762761181a436` for the full IDF vs Hamas match, seed 1, normal).
2. **Simulation architecture:**
   - 10 Hz tick and command queue ordering (tick, player, sequence).
   - The list of commands and what each does.
   - Events (output only), `StateHasher`, `SimLoop.Step`, and the determinism rules.
3. **Data model:** each JSON file and its key fields, and how the validator checks them.
4. **Mechanics, with formulas and the data values they use:**
   - Movement and pathfinding.
   - Vision and fog of war (line-of-sight blockers, update rate, remembered terrain).
   - Combat: target choice, range-band accuracy, moving penalty, directional cover (heavy and light, direction threshold), per-soldier damage, vehicle front and rear armor with penetration, setup weapons.
   - Suppression thresholds and decay.
   - Retreat, reinforce and healing.
   - Territory: Voronoi sectors, neutralize-then-capture, contested points, supply connection.
   - Income, VP ticket drain, victory and defeat conditions, surrender.
   - Production queues: cost reservation, cancel refunds, population cap.
   - Construction: placement rules, engineers, sandbags.
   - AI: difficulty presets, build orders, unit mix, cappers, attack and defend, retreat thresholds, fog-respecting memory.
5. **Rosters per faction** (generated tables):
   - Units: cost, population, squad size, HP, speed, sight, build time, weapons, and the building that produces them.
   - Structures: tier, cost, build time, HP, footprint, requirements, what they produce.
   - All weapons with their stats.
   - The deferred units.
6. **Map:** Border Ridge Outpost (size, mirrored layout, sector types and count, obstacles, ground zones).
7. **Player-facing spec:**
   - Controls and the command card.
   - HUD layout and on-screen overlays (health bars, suppression tags, capture rings, cover preview).
   - Fog and territory border visuals, and camera behavior.
   - Main menu, pause menu and end screen.
   - Audio and effects per weapon or event.
   - Each faction's visual identity (building and unit designs).
   - Test and launch options.
8. **Tests and tools:** test coverage by mechanic, MatchRunner, how to check determinism.
9. **Known issues and balance state:** Hamas strong, Hard vs Easy not yet measured, Windows hash not yet confirmed, and so on.
