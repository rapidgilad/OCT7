# Plan: move the presentation layer from Godot to Unity

## Context
- **v0.1 is done:** a first playable 1v1 skirmish against AI with all three factions. It is built as:
  - an **engine-free deterministic simulation** (`sim/`, pure C#);
  - **data files** (`game/data/*.json`);
  - a **Godot 4.5.1 .NET presentation layer** (`game/`).
- **Moving to Unity:** the owner is taking development to their desktop and moving the presentation to Unity, for Unity's art, tools and asset ecosystem.
- **What moves and what doesn't:**
  - The sim was built engine-free (C# 9, `netstandard2.1`) precisely so this move doesn't touch the game rules.
  - **The port is a presentation port.** Every rule, number and AI decision already lives in `sim/` and `game/data/`, and must be reused, not rewritten.
- **Read first:**
  1. [`../10-implementation-reference.md`](../10-implementation-reference.md): the game as built. It is the parity specification.
  2. `CLAUDE.md`: project rules (determinism, data-driven design, content rules).
  3. This plan.

## Principles (non-negotiable)
1. **One simulation.**
   - Unity uses the `sim/` code as is: the same source, or a DLL built from it.
   - No game rule is reimplemented in MonoBehaviours.
   - If Unity needs a gameplay change, make it in `sim/`, with tests, so every host gets it.
2. **One data source.** `game/data/*.json` stays the source of truth.
   - Unity may copy the files into `StreamingAssets` as a build step, but never edits the copies.
   - ScriptableObjects, if used at all, are generated read-only views.
   - The tests and MatchRunner read the same JSON.
3. **Presentation only reads and sends commands.**
   - Views read sim state and interpolate between ticks (`PrevPosition` → `Position`).
   - Input becomes `Command` objects queued on the sim.
   - Nothing in Unity writes sim state.
4. **Hash parity before gameplay.** Unity must reproduce the reference hashes in docs/10 §1.4 before any gameplay UI is built. If the hashes differ, the port is not running the same game.
5. **Godot stays until parity.**
   - `game/` and its CI keep building playable Windows builds until Unity reaches U2.
   - Don't delete or break it before U4.
6. **Every approved plan is committed** to `docs/plans/` before implementation. Any mechanic change also updates docs/10.

## Milestones

### U0: the sim runs inside Unity and its hashes match (gate)
**Work:**
- Create the Unity project and bring `sim/` in (see the "Including the sim" decision below).
- Write a `UnityDataSource`, the equivalent of `game/scripts/GodotDataSource.cs`:
  - It reads the JSON files into `GameDataFiles`, then calls `GameDataLoader.FromJson`. The sim leaves file I/O to the host.
  - It reads the map list from `maps/maps.json`.
- Write a minimal host:
  - Build a match with `MatchSetup` and run an AI for each side.
  - Call `SimLoop.Step(sim, ais, buffer)` once per tick.
  - Print `sim.ComputeStateHash().ToString("x16")`.
- Run that host three ways:
  1. As an Edit Mode test (Unity Test Framework).
  2. From a batch-mode command line (`-batchmode -nographics -executeMethod …`).
  3. In a built Windows player.

**Acceptance:**
- All three docs/10 §1.4 hashes match, in the Editor and in a Windows build:

  | Run | Must end at tick | Winner | Hash |
  |---|---|---|---|
  | 600-tick run | 600 | — | `abc254d66a095c02` |
  | Full IDF vs Hamas match | 10560 | 1 | `d2b762761181a436` |
  | Full Hezbollah vs IDF match, hard | 11844 | 0 | `015b300ee8927c38` |

- `dotnet test tests/OCT7.Sim.Tests` and MatchRunner still pass. The sim was not modified, or was modified only in ways that keep all hashes.

**If the hashes differ:**
- The sim uses only IEEE-exact math (`Sqrt`, `Floor`, `Ceiling`, `Abs`, `Min`, `Max`, `Clamp`, `Round`; no trigonometry or `Pow`), so cross-runtime differences should be rare.
- Suspects, in order:
  1. Data not loaded identically (a missing or different file, or JSON options).
  2. Host loop order (AI think → enqueue → `Step`, exactly once per tick).
  3. Runtime float precision: some Mono configurations evaluate `float` math at double precision, and IL2CPP's C++ compiler may fuse multiply-adds.
- Use the Mono scripting backend until IL2CPP is proven separately.
- Compare per-tick hashes against the Godot or MatchRunner run to find the first tick that diverges.

### U1: playable greybox match
Simple shapes, full gameplay loop.

**Work:** build every interaction in docs/10 §10.2–10.4 with simple visuals:
- Ground and obstacle boxes; squads as team-colored capsules, one per model; vehicles as boxes.
- RTS camera: pan, edge pan, zoom, Q/E rotate, fixed 55° pitch.
- Click and box selection; double-click; control groups.
- Context orders: move with cover snap, attack, assist construction, rally point.
- Command card with hotkeys; production queues with cancel; building placement with ghost and rotation.
- Retreat, Reinforce, Stop.
- Fog of war; territory overlay and capture rings.
- HUD: resources, tickets, clock, selection card, message feed.
- Minimap.
- Menu → match → pause → end screen.

Interpolate views with alpha = accumulated time / `SimConfig.TickSeconds`. Read `sim.Events` after **every** `Step()`: they are cleared each tick, and one frame may run several ticks.

**Acceptance:**
- A full match against the Normal AI can be played to victory and to defeat with mouse and keyboard.
- No sim state is written from Unity code (review checklist).

### U2: v0.1 parity
**Work:** match everything in docs/10 §10:
- Faction visual identity: distinct building per structure id, distinct soldiers per role, Merkava, Namer, Technical.
- Effects per event.
- Audio per weapon, with the delayed impacts and fog-aware playback.
- Overlays: health bars, SUPPRESSED, PINNED and RETREAT tags, cover preview.
- Vegetation and ground detail.

Art can be:
- ported from the procedural Godot models (`game/scripts/Visual/`);
- replaced with Asset Store packs;
- a mix of both.

Launch options needed for testing (docs/10 §10.7): `--smoke-test N [--full-match]`, `--showcase`, `--demo --fast-forward N`, `--screenshot PATH --after-frames N`, plus the match setup flags.

**Acceptance:**
- The parity checklist below is fully ticked.
- The owner plays both builds side by side and prefers or accepts the Unity build.

### U3: Unity upgrades
Asset Store art and animation, particle systems, URP post-processing, recorded or library sounds, better terrain.

**Rule:** visual and audio only. Any change that affects gameplay goes through `sim/` with tests, and is reflected in docs/10.

### U4: Unity builds in CI; retire Godot
- Unity builds in CI (for example GameCI, which needs Unity license secrets in the repository settings).
- Publish to the rolling `dev-latest` release instead of the Godot zip.
- Tag the last Godot state (`godot-final`), then remove `game/` except `game/data/`. Optionally move `game/data/` to a neutral `data/` and update the loaders, tests, MatchRunner and CLAUDE.md in the same commit.
- Update CLAUDE.md commands and docs/08.

**Acceptance:**
- CI is green.
- The Windows zip comes from Unity.
- The hash test runs in CI against the Unity build, or at least as an Edit Mode test.

## Decisions left to the desktop Claude (with the constraints that bind them)

| Decision | Recommendation | Constraints |
|---|---|---|
| Unity version | Unity 6 LTS (6000.0.x) | Must compile C# 9 and `netstandard2.1` (the sim's targets). Record the exact version in `ProjectSettings/ProjectVersion.txt` and in the decision log. |
| Render pipeline | URP | Top-down RTS with many units. Most RTS and military Asset Store packs target URP. HDRP is overkill. |
| Scripting backend | Mono first | IL2CPP only after the U0 hashes are re-verified under it. |
| Including the sim | **DLL first:** `dotnet build sim -c Release`, then a script copies `OCT7.Sim.dll` (+ `.pdb`) and its dependencies into `Assets/Plugins/OCT7/` | One source copy only. Unity compiles every `.cs` under `Assets/` or a local package, **including generated files in `sim/obj/`** (for example `OCT7.Sim.AssemblyInfo.cs`). So pointing Unity at the `sim/` folder directly (symlink or local package) needs those folders excluded. A local package with an asmdef (`noEngineReferences: true`) is a later option for in-editor source debugging. |
| JSON inside Unity | Keep `System.Text.Json` (the sim's dependency, version 8.0.5) as plugin DLLs, with their `netstandard2.0` dependencies (`System.Memory`, `System.Buffers`, `System.Runtime.CompilerServices.Unsafe`, `System.Text.Encodings.Web`, `Microsoft.Bcl.AsyncInterfaces`, `System.Threading.Tasks.Extensions`, `System.Numerics.Vectors`, as needed), or install it with NuGetForUnity | Changing the sim's JSON library changes the test and tool code too, so avoid it. Comments and trailing commas in the JSON must keep working. |
| Data location at runtime | Copy `game/data/**` into `StreamingAssets/data/` on build or in an editor menu | Never edit the copies. Desktop Windows can read them with `File.ReadAllText`. |
| Tick driver | `Update` with an accumulator, calling `SimLoop.Step` per 0.1 s tick | Exactly one `SimLoop.Step` per tick; read events after each step. Pause stops the accumulator. Avoid tying ticks to the physics `FixedUpdate` rate. |
| Input | Input System package | Must cover docs/10 §10.2 exactly. Hotkeys are by physical key. |
| UI | uGUI or UI Toolkit | Layout and behavior must match docs/10 §10.3. Disabled buttons dim; tooltips; message feed rules. |
| Fog of war rendering | A texture written from `VisibilityGrid` (three levels), blurred, sampled by the ground shader or a projector | Hide enemies outside vision. Remember explored cells. |
| Art | Greybox (U1), then procedural port or Asset Store packs (U2/U3) | Content rules above. Distinct silhouettes per faction and tier. |
| Git hygiene | Unity `.gitignore` (`Library/`, `Temp/`, `Logs/`, `UserSettings/`, `obj/`, `Build*/`); Visible Meta Files; Force Text serialization; LFS for binary art (`.gitattributes` already routes `.fbx`, `.glb`, `.blend`, `.psd`, `.tga`, `.wav`, `.ogg`, fonts and `game/assets` images through LFS; add `unity/Assets/**/*.png` and similar) | Commit `.meta` files. Never commit `Library/`. |

## Sync and working rules
- **The desktop is now the primary workplace.** A ZIP has no git history and can't push. Switch to a clone:
  ```
  git clone https://github.com/rapidgilad/OCT7.git OCT7
  cd OCT7
  git checkout claude/coh-rts-game-design-06vm8t   # the repository's default branch today
  git lfs install && git lfs pull
  ```
- **If work was already done inside the ZIP copy:**
  1. Copy only the new or changed files (for example a new `unity/` folder) into the fresh clone.
  2. Check them with `git status` and `git diff`.
  3. Commit and push.
  - Never copy the ZIP's whole tree over the clone: it would revert anything pushed since the ZIP was downloaded.
- **Cloud session:** it makes no further changes unless the owner asks.
  - If asked, it is well suited to engine-free work (`sim/`, tests, data and balance with MatchRunner) while the desktop does Unity work.
  - Each side pulls before starting and pushes when done.
- **Every approved plan goes into `docs/plans/`** as `YYYY-MM-DD-NN-short-name.md`, with a status header, before implementation starts.
- **Every change to a mechanic updates docs/10** in the same commit.

## Risks
| Risk | Mitigation |
|---|---|
| Hash mismatch under Unity's runtime | U0 gate. Use the Mono backend. Bisect with per-tick hashes. Fixed-point math in the sim is the last resort: it is a large change and would invalidate the reference hashes. |
| Rules leak into MonoBehaviours during UI work | Principle 1, plus a review checklist item per milestone. Gameplay changes go through `sim/` with tests. |
| Data drift between `game/data` and `StreamingAssets` | Copy step only. Copies are read-only. Optionally a hash of the data shown in the build stamp. |
| Losing the playable build during the port | Godot CI keeps publishing until U4. |
| Asset Store content conflicting with the content rules | Review every pack against docs/01 before import. Replace insignia, flags and religious-building shapes. |
